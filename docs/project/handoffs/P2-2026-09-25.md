## Delivered

- `local_service/capture_bridge.py` discovers private LAN IPv4 addresses, prefers physical Wi-Fi over VPN/virtual routes, and starts an independent listener only while a Capture Session is active.
- Admin/Desktop API remains loopback-only on `127.0.0.1:8765`. Capture uses the selected private IPv4 and port `8766`; its surface has no admin routes or CORS.
- Migration 002 stores Capture Session lifecycle/current Submission, a SHA-256 token hash, and idempotent session-to-Submission progress. Raw tokens are generated with 32 bytes of cryptographic randomness, returned only to the desktop for QR generation, kept in process memory, and sent to phones only by the QR URL. End, expiry, and process restart invalidate the token and stop the listener.
- `local_service/capture_page.html` provides the iPhone Safari file/camera input with rear-camera preference, preview, retake, keep-and-upload per page, page list/thumbnails, delete/reindex, refresh recovery through session storage, and explicit finish confirmation. No iOS app, getUserMedia streaming, OCR, VLM, or image-quality AI was added.
- Each image is limited to 10 MiB; the service rejects empty data, MIME/signature mismatches, and unsupported formats. Files use internal page UUID names; stored metadata includes page/submission ID, page index, original filename, MIME, byte size, upload time and content SHA-256. Uploads require the current Submission ID and a UUID idempotency key.
- Only confirmed finish transitions the active Submission through READY to QUEUED and adds one job. The next active roster student can be captured while the prior job runs; finishing the last student leaves the class complete rather than restarting at the first student.
- Desktop receives a generated QR, current student/page count, roster progress, background job status, and session end control.

## Browser E2E evidence

Verified in the in-app desktop browser using disposable test data and three local 1×1 PNG fixtures:

1. Created a test class, two students and an assignment through the Desktop UI.
2. Started a class Capture Session through the Desktop UI; QR was generated for the selected LAN address `192.168.31.89:8766`. The QR URL included only the route and random token, without roster information.
3. Opened the phone-equivalent Safari page, confirmed the assignment/current student and added three pages one at a time. Each confirmed page uploaded immediately.
4. Confirmed page uploads did not change the current student. Selected a new preview and used **重拍**; the staged page was discarded without increasing the count.
5. Opened the delete confirmation and cancelled once; all three pages remained. Confirmed deletion of page 2; the former page 3 appeared at index 2. Uploaded a replacement and refreshed; the three-page list and order restored.
6. Confirmed finish for the first student; the phone page advanced to the second student. Uploaded a page for the second student; the Mac showed that student as current with one page while the first student appeared in the background queue as **排队中**.
7. Confirmed finish for the last student; the phone page showed **本班拍摄完成**. The Mac showed 2/2 students complete and both queued submissions. A temporary service without a worker was used only to keep queue entries visible during UI verification.
8. Ended the Capture Session through the Desktop UI. The LAN Capture listener stopped; the local admin service and Vite dev server were then shut down.

All browser fixtures were disposable local 1×1 PNGs with no student content, stored under `/tmp` and not added to Git. The actual test token is not retained in project docs.
